# KERN — TECHNICAL REQUIREMENTS DOCUMENT (TRD)

> **Version:** 1.0 | **Date:** 2026-11-18 | **Status:** Design specification; not an implementation report.  
> **Owner:** Engineering | **Related:** [prd.md](prd.md) and [architecture.md](architecture.md)  
> **Mandate:** All Kane integrations must be real. Every visible result must be traceable to an actual run or explicitly marked demo fixture.

## 1. Technical objectives

Develop a locally runnable full-stack web application that stores merchant-approved promotional claims, translates them into fixed browser challenges, executes those challenges via authenticated **Kane CLI**, evaluates observed data against deterministic expectations, surfaces evidence, and supports an auditable, bounded coding-agent repair with an independent Kane rerun.

A successful P0 deployment does **not** require live ad accounts, payment rails, automatic GitHub PR creation, a remote Kane cloud runner, or production-grade multi-tenancy.

## 2. Recommended implementation stack

| Layer | P0 choice | Rationale | Alternative / condition |
|---|---|---|---|
| Application | Next.js App Router + strict TypeScript | One codebase for UI and application API | Existing compatible framework if repository already exists |
| UI | React + Tailwind CSS | Fast accessible interface + cohesive design | CSS modules |
| Persistence | SQLite (`better-sqlite3` or typed ORM) | Local-first, no external credentials | Hosted Postgres only if already configured |
| Background jobs | Dedicated trusted Node process/worker | Browser CLI must outlive API request; safer than serverless execution | A single local supervisor plus persistent job table |
| Browser verification | `@testmuai/kane-cli`, installed Chrome | Required sponsor-native real browser execution | None as product verification engine in P0 |
| Coding agent | **One:** Pi CLI or Codex CLI | Authorized source repair; pick installed/authenticated option | If unavailable, transparent terminal-driven agent loop, not simulated UI automation |
| AI promise assistant | Optional model call with structured output | Helps interpret ad copy | Manual typed claim entry MUST work offline |
| Evidence | Local private artifact directory + DB metadata | Supports reproducible audit packs | Object store later |
| Deployment | Local execution with optional hosted dashboard | Avoid serverless spawning a heavy browser | Hosted worker only with real credentials and browser runtime |

## 4. Typed domain contracts

### 4.1 Promise contract

```ts
type PromiseType = 'free_shipping_threshold'; // P0
type Money = { currency: 'USD'; cents: number };
type PromiseContract = {
  id: string; campaignId: string; version: number;
  type: PromiseType;
  thresholdBasis: 'after_discount_merchandise_subtotal';
  operator: 'greater_than_or_equal';
  threshold: Money; // 5000 cents
  qualifyingProductIds: string[];
  destinationCountry: 'US';
  shippingMethod: 'standard';
  expectedEligibleShipping: Money; // 0
  expectedIneligibleShipping: Money; // 900
  adTextSnapshot: string;
  destinationOrigin: string;
  approvedAt: string;
  approvedBy: string;
  specSha256: string;
};
```

All money is integer cents. No float comparison. All contracts are serialized using documented canonical field order before hash calculation. Explicitly define free-shipping threshold after discounts and before tax/shipping. The cart's eligibility must be computed from the *same business definition* in the oracle and demo fixture, but the browser observation must come independently from the actual UI/Kane to avoid a tautological check.

### 4.2 Scenario

```ts
type ShopperScenario = {
  id: string; contractId: string;
  shopperLabel: 'eligible' | 'negative_control';
  items: Array<{ productId: string; qty: number }>;
  country: 'US'; shippingMethod: 'standard';
  expectedCartSubtotalCents: number;
  expectedShippingCents: number;
  status: 'READY' | 'RETIRED';
};
```

**Fixture:** product IDs and prices create after-discount subtotals of `$60.00` and `$35.00`; corresponding expected shipping is `$0.00` and `$9.00`. Run the same products/quantities before and after a fix. The desired behavioral bug is **shipping calculation threshold too high**, deliberately present as real source code and verified through the interface.

### 4.3 Audit and result

```ts
type AuditStatus =
  | 'QUEUED' | 'RUNNING'
  | 'FAILED_PROMISE' | 'VERIFIED_FOR_TESTED_CONDITIONS'
  | 'INCONCLUSIVE' | 'INFRA_ERROR' | 'CANCELLED';

type KaneExecution = {
  id: string; auditId: string; scenarioId: string;
  kaneVersion: string; launchedAt: string; finishedAt?: string;
  childExitCode?: number; terminalStatus?: 'passed' | 'failed';
  finalState?: Record<string, unknown>;
  testManagerUrl?: string;
  evidencePath?: string; evidenceSha256?: string;
  evidenceValid?: boolean; failureReason?: string;
};
```

Store a row per scenario execution. The audit verdict is an aggregation of required scenarios. No single `terminalStatus: passed` should override a failed monetary comparison or missing receipt evidence.

Enforce foreign keys, unique `(campaign_id, version)`, immutable issued receipts, and at-most-one running worker lease per audit. Avoid persisting secrets or personal shopper account contents. For hackathon, a demo merchant account may be seeded and clearly identified; auth must be added before publicly exposing privileged repair endpoints.

## 6. Internal API contract (proposed, NOT Kane API)

All paths below are **Kern application endpoints**, not official TestMu or Kane endpoints.

| Method | Path | Auth | Purpose |
|---|---|---|---|
| POST | `/api/campaigns` | Local authenticated merchant | Create draft campaign |
| GET | `/api/campaigns` | Same | List owned campaigns |
| POST | `/api/campaigns/:id/promises/preview` | Same | Propose typed interpretation |
| POST | `/api/campaigns/:id/promises/approve` | Same | Validate + freeze contract |
| GET | `/api/campaigns/:id/challenge` | Same | Read scenario expectations |
| POST | `/api/audits` | Same | Queue Kane audit for frozen contract |
| GET | `/api/audits/:id` | Same | State, results, findings, evidence metadata |
| GET | `/api/audits/:id/events` | Same | Real status events via polling or SSE |
| POST | `/api/findings/:id/repairs` | Local operator/admin | Create bounded repair case |
| POST | `/api/repairs/:id/approve` | Human operator | Approve proposed patch |
| POST | `/api/repairs/:id/reverify` | Local operator/admin | Queue unchanged challenge |
| GET | `/api/receipts/:id` | Authorized reader | Read redacted structured receipt |

### Representative payload

```json
{
  "campaignId": "camp_demo_001",
  "contractId": "contract_v1",
  "scenarioIds": ["qualifying_60", "control_35"],
  "requestKind": "initial_audit"
}
```

`POST /api/audits` returns `202 Accepted` plus an audit ID after safely persisting the job. It must not return an invented final verdict. Validate ownership, contract frozen status, scenario IDs and approved destination origin on *every* call. Use an idempotency key to prevent repeated button clicks from queuing duplicate runs.

## 7. Kane CLI runner integration

### 7.1 Core command (illustrative objective; adjust selectors to real demo store)

```bash
kane-cli run \
  "Go to http://localhost:3000/demo-store. Add the eligible fixture item to make a 60 USD after-discount merchandise subtotal, proceed to the shipping quote screen, store the displayed shipping charge as 'observed_shipping', store the cart subtotal as 'observed_subtotal', and verify standard shipping is 0 USD" \
  --agent --headless --timeout 180
```

Use a distinct `$35` control run, requiring `$9` shipping. **Do not depend on a hypothetical `--json` flag or on synthetic output.** Commands must run from trusted code, with child-process spawn argument arrays and `shell: false`.

### 7.2 Parser contract

- Parse newline-delimited JSON from stdout; stderr is separate and redacted.
- Progress objects may contain `step/status/remark`; they are for UI and diagnostics, **not** the stable final verdict API.
- For one-shot `run`, expect `type: "run_end"` with `status`, `final_state`, `summary`, `session_dir`, optional `test_url` and other documented values.
- Require child process exit code **0** and `run_end.status === 'passed'` for a browser-assertion pass, then independently compare typed observed amounts with the contract.
- Exit **1** represents a Kane-executed failed objective; classify as `FAILED_PROMISE` only when evidence and observed mismatch establish the underlying business failure. Otherwise `INCONCLUSIVE`.
- Exit **2** means setup/infrastructure/auth; exit **3** means timeout or cancellation. Neither is a merchant failure; classify `INFRA_ERROR` or `CANCELLED`.
- If `run_end` missing, amount unparsable, pack unavailable/unvalidated, or actual location not approved → `INCONCLUSIVE`/`INFRA_ERROR` and no verified receipt.
- Kane versions differ; implement an adapter with versioned fixtures from **real CLI captures**. Do not assume `testmd` emits the same terminal event (`test_md_done` is documented for saved test completion).

### 7.3 Evidence lifecycle

Locate the actual `.evidence` path reported or produced by the installed Kane release. Calculate SHA-256; run official `kane-cli evidence validate <path>` where available. Save a local reference in the DB and link to the local viewer or sanitized exported artifacts. Test Manager URL is optional and must be copied only from a real `run_end` field. Do not commit private packs to Git; commit sanitized proof summaries or reproducibility instructions.

### 7.4 Requirements-linked testing

The official assurance flow can ingest **`prd.md`**, extract/review use cases, design test cases, and report covered versus owed criteria. Review generated tests instead of treating model-inferred cases as authoritative.

```bash
kane-cli context ingest ./docs/prd.md
kane-cli context extract
kane-cli context review
# use actual approved use-case identifier, not a fabricated ID:
kane-cli design tests --use-case <approved-use-case-id>
kane-cli cover
```

For a saved test, use `kane-cli testmd run ./tests/kane/qualifying_shipping_test.md --agent --headless`; capture **`test_md_done`** and exit status. Run generated or approved saved tests only after understanding their requirements linkage. P0 may use `run` for dynamic merchant challenges and additionally commit a testmd test for the canonical demo.

## 8. Deterministic promise oracle

The trust boundary is essential: **browser observations must come from Kane; expectations come from the merchant-approved frozen contract.** Do not let a language model decide both sides.

```ts
function expectedShipping(contract: PromiseContract, subtotalCents: number): number {
  const qualifies = subtotalCents >= contract.threshold.cents;
  return qualifies
    ? contract.expectedEligibleShipping.cents
    : contract.expectedIneligibleShipping.cents;
}
```

The same function is NOT imported into the demo store's shipping implementation. The whole test is to catch a defect there. After receiving Kane's observed amount, parse locale/currency explicitly; reject ambiguous strings; compare integer cents. An order's checkout rendering and its backend quote must agree for the supported fixture.

### Verdict aggregation example

| Scenario | Kane completed | Observed amount | Expected | Result |
|---|---|---|---|---|
| Eligible $60 | Yes | $9 | $0 | Failed promise |
| Control $35 | Yes | $9 | $9 | Passed control |
| Aggregate | Both complete | — | — | **FAILED_PROMISE** |

After repair, the same scenario IDs must yield $0 and $9 respectively. If the $35 control incorrectly yields $0, aggregate still fails. The system must never award a pass to a repair that simply makes all shipping free.

## 9. Repair execution interface

**P0 preferred:** human-reviewed, local-only adapter that invokes an authenticated coding agent in a sandbox worktree. The agent receives immutable contract JSON, sanitized Kane summary/evidence location, current source revision, allowed files and exact acceptance criteria. It must be instructed never to edit test expectations or the comparator. The adapter records actual agent invocation and changed files.

```ts
interface RepairAdapter {
  diagnoseAndPropose(input: {
    repairId: string;
    allowedWorkingTree: string;
    allowedPaths: string[];
    contractHash: string;
    safeEvidenceSummary: string;
    originalScenarioIds: string[];
  }): Promise<{ changedFiles: string[]; patchPath: string; logPath: string }>;
}
```

If Codex is selected, `codex exec` is documented for non-interactive operation; if Pi is selected, its CLI print/RPC mode may be used after inspecting installed version help. **Do not invoke a self-written invented CLI syntax.** Preferred workflow: create isolated branch/worktree; run agent bounded to store shipping files; inspect diff, lint/tests; approve; apply; execute Kane again. A manual coding-agent run connected through a recorded evidence ledger is an acceptable fallback **only if labeled accurately**, not represented as autonomous web-app behavior.

## 10. Security, authorization and responsible automation

- **SSRF / URL policy:** reject non-http(s), username/password URLs, redirects outside allowlisted origin, DNS rebind and private addresses on remote-untrusted targets. For P0, allow only explicit owned demo-origin loopback URL. Separate local authorization from user-submitted targets.
- **Command execution:** worker accepts `scenarioId`, not arbitrary command strings or user shell input. Build objectives from server-side templates and validated values. Spawn CLI without shell.
- **Prompt injection:** browser page content and ad text are untrusted data. Never let them override system policy, task boundaries, network/file access or agent instructions.
- **Source edits:** sandbox worktree, allowed paths, diff inspection, separate approval; block `.env`, credentials, tests, canonical contract, parser and security code from automatic repair.
- **Secrets:** local `.env`, never stored in a receipt; redact stdout/stderr and avoid personal browser profiles.
- **Payments and personal data:** fixture shoppers, fake contact information, no charge submission; stop before a real purchase.
- **Idempotency and concurrency:** one active audit per frozen contract scenario set; unique request token; time-bound worker leases; safe restart recovery.
- **Audit integrity:** append-only events and issued receipts; hash raw and canonical artifacts; immutable original claim.
- **Rate/cost:** cap runs per minute/user, wall-clock timeout, max concurrent processes and repair retries.
- **Access:** local-only trusted operator controls P0; use real auth/RBAC before public deployment of repair endpoints.

## 11. Nonfunctional requirements

| ID | Requirement / measurable test |
|---|---|
| NFR-01 | Determinism: at least 2 canonical fixtures produce stable expected outcomes over 5 unit-test iterations |
| NFR-02 | No fabricated proof: invalid/missing CLI output never creates verified receipt; integration tests cover this |
| NFR-03 | Recoverability: app restart retains audit state and records unfinished jobs as retryable/error, never falsely complete |
| NFR-04 | Reliability: no unbounded repair/retry loop; max 2 agent repairs, CLI timeout 180 seconds per scenario initially |
| NFR-05 | Observability: audit ID and scenario ID propagated to logs/artifact metadata; timestamps and durations retained |
| NFR-06 | UX: responsive down to mobile width, accessible status text and keyboard use for P0 core path |
| NFR-07 | Privacy: no secrets in receipt/log export; evidence stored privately by default |
| NFR-08 | Verification: independent control case required; no browserless substitute for Kane sponsor check |
| NFR-09 | Setup: documented Windows/WSL/Linux choices and Chrome requirements; no undocumented managed services |
| NFR-10 | Reproducibility: fresh clone plus documented env/tools can rerun canonical demo; CI/source artifacts contain no secrets |

## 12. Test matrix

1. Claim with missing threshold → approval blocked.
2. Claim with contradictory country or ambiguous threshold basis → require clarification.
3. Approved contract hash changes after attempted edit → reject mutation.
4. $60 pre-fix eligible cart → Kane sees $9 shipping; `FAILED_PROMISE` with actual evidence.
5. $35 pre-fix control → Kane sees $9; control passes.
6. Post-fix $60 eligible cart → Kane sees $0; positive passes.
7. Post-fix $35 control → Kane sees $9; negative passes.
8. Store behavior wrongly makes all shipping free → negative control fails.
9. Fake green `run_end` without pack or price extraction → no verified receipt.
10. Kane exit 2 or missing login → `INFRA_ERROR`, not `FAILED_PROMISE`.
11. Kane timeout → explicit timeout error; no fabricated observation.
12. Disallowed redirect/origin → stop safely.
13. Repair agent touches a forbidden file → reject patch.
14. Changed test expectations after failure → contract hash guard blocks verification.
15. Second repair attempt also fails → escalate, no infinite retries.
16. Duplicate audit click → one queued job.
17. Redacted receipt contains no secrets.
18. Restart worker midrun → interrupted state reclassified and discoverable.

## 13. Definition of done

- Core web routes and real demo checkout functional; code committed.
- Actual Kane authenticated execution through dedicated worker; terminal event and exit code captured.
- Required positive + negative scenario both run in Chrome; genuine before/after proof.
- Repair causes an actual constrained source diff, not a fixture flip masked as automation.
- Readable receipt includes actual evidence pack references and scope disclaimers.
- Unit/integration tests for comparator, parser, states and security cases pass.
- README reproduction and YouTube walkthrough exist; submission checklist completed before official deadline.
